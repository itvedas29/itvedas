Bash Networking Scripts: Automate Network Tasks from Scratch

Bash scripts automate repetitive network tasks by combining command-line tools like ping, curl, ssh, and nslookup into reusable workflows. Instead of manually running commands dozens of times, you write a script once and execute it instantly. This guide teaches you to build production-ready networking scripts that save hours of manual work.

Why Use Bash for Network Automation?

Bash is the de facto standard for Unix-like systems because it's available everywhere—servers, cloud instances, containers. Unlike Python or Perl, you don't need to install dependencies. Bash scripts run immediately on any Linux or macOS system. It excels at orchestrating existing CLI tools and handling text processing, which is core to networking tasks.

Network administrators use Bash for monitoring uptime, bulk server configuration, automated backups, log analysis, and incident response. The skills transfer directly to DevOps, cloud engineering, and systems administration roles.

Setting Up Your First Bash Script

Every Bash script starts with a shebang—the line that tells the system to interpret the file as a Bash script.

#!/bin/bash

# This is a comment
echo "Hello from Bash!"

To make this executable:

chmod +x script.sh
./script.sh

The shebang #!/bin/bash must be the first line. Without it, the system won't know how to run your script. Always use this rather than relying on the user to call bash script.sh manually.

Building a Host Connectivity Monitor

One of the most practical networking scripts checks whether multiple servers are reachable. This script pings a list of hosts and reports their status.

#!/bin/bash

# Define target hosts
HOSTS=("8.8.8.8" "1.1.1.1" "example.com" "192.168.1.1")
TIMEOUT=2

echo "=== Host Connectivity Report ===" 
echo "Timestamp: $(date)"
echo

for host in "${HOSTS[@]}"; do
  if ping -c 1 -W $TIMEOUT "$host" &> /dev/null; then
    echo "✓ $host is ONLINE"
  else
    echo "✗ $host is OFFLINE"
  fi
done

This script loops through each host, sends a single ping request with a 2-second timeout, and prints the result. The &> /dev/null suppresses output so you only see your custom status messages. This is the foundation for uptime monitoring—extend it by logging results to a file and setting up cron jobs for continuous checks.

Improving the Monitor with Logging

#!/bin/bash

HOSTS=("8.8.8.8" "1.1.1.1" "example.com")
LOGFILE="/var/log/host_monitor.log"
TIMEOUT=2

{
  echo "[$(date '+%Y-%m-%d %H:%M:%S')] Host Connectivity Check"
  for host in "${HOSTS[@]}"; do
    if ping -c 1 -W $TIMEOUT "$host" &> /dev/null; then
      echo "✓ $host is ONLINE"
    else
      echo "✗ $host is OFFLINE"
    fi
  done
  echo
} >> "$LOGFILE"

Now results append to a log file with timestamps. You can run this every 5 minutes via cron and build a historical record of network health. The curly braces redirect all output to the file without repeating >> on each line.

Automating SSH Operations Across Multiple Servers

Managing several servers manually wastes time. This script executes commands remotely on multiple hosts simultaneously.

#!/bin/bash

SERVERS=("user@server1.example.com" "user@server2.example.com" "user@server3.example.com")
COMMAND="uptime"

for server in "${SERVERS[@]}"; do
  echo "Executing on $server..."
  ssh -o ConnectTimeout=5 "$server" "$COMMAND"
  echo "---"
done

Replace COMMAND with any shell command—update packages, check disk space, restart services. The ConnectTimeout=5 prevents hanging if a server is down. For production use, set up SSH key authentication so you don't need to enter passwords each time.

Running Commands in Parallel

If you have many servers, sequential execution is slow. Background jobs speed this up dramatically:

#!/bin/bash

SERVERS=("user@server1" "user@server2" "user@server3" "user@server4")

for server in "${SERVERS[@]}"; do
  ssh "$server" "free -h; df -h" > "/tmp/${server##*@}.txt" &
done

wait

echo "All servers checked. Results:"
cat /tmp/*.txt

The ampersand & runs each SSH command in the background. wait pauses the script until all background jobs finish. This executes all four servers concurrently instead of waiting for each one sequentially. Output goes to separate files so results don't overlap.

DNS and Network Diagnostics

Automating DNS lookups and network diagnostics saves troubleshooting time. This script performs multiple DNS queries and tests resolution.

#!/bin/bash

DOMAINS=("example.com" "google.com" "cloudflare.com")
NAMESERVER="8.8.8.8"

echo "=== DNS Resolution Report ===" 
echo "Using nameserver: $NAMESERVER"
echo

for domain in "${DOMAINS[@]}"; do
  echo "Domain: $domain"
  
  # Get A record
  A_RECORD=$(dig +short "$domain" A @"$NAMESERVER" | tail -1)
  if [ -n "$A_RECORD" ]; then
    echo "  A Record: $A_RECORD"
  else
    echo "  A Record: NOT FOUND"
  fi
  
  # Get MX record
  MX_RECORD=$(dig +short "$domain" MX @"$NAMESERVER" | head -1)
  if [ -n "$MX_RECORD" ]; then
    echo "  MX Record: $MX_RECORD"
  else
    echo "  MX Record: NOT FOUND"
  fi
  
  echo
done

This queries A and MX records for multiple domains. The +short flag strips formatting. You can extend this to check NS records, SPF records, or test DNS propagation across multiple servers.

Port Scanning and Service Verification

Check if services are listening on specific ports without installing nmap.

#!/bin/bash

HOST="example.com"
PORTS=(22 80 443 3306 5432)

echo "Scanning ports on $HOST..."
echo

for port in "${PORTS[@]}"; do
  timeout 1 bash -c "cat < /dev/null > /dev/tcp/$HOST/$port" 2>/dev/null
  if [ $? -eq 0 ]; then
    echo "✓ Port $port is OPEN"
  else
    echo "✗ Port $port is CLOSED"
  fi
done

This uses pure Bash—no external tools needed. The /dev/tcp/ device file connects to a host:port combination. If the connection succeeds, the port is open. Timeout prevents hanging on unresponsive ports.

Parsing and Processing Network Configuration

Scripts often need to extract network data and transform it. This example parses network interface information.

#!/bin/bash

echo "=== Network Interface Summary ===" 
echo

ip addr show | grep -E "^[0-9]|inet " | awk '
  /^[0-9]/ {
    interface = $2
    gsub(/:/, "", interface)
  }
  /inet / && interface != "lo" {
    gsub(/\/.*/, "", $2)
    printf "%-10s %s\n", interface, $2
  }
'

This pipes network data through grep and awk to extract active interfaces and their IP addresses. Breaking output down into readable tables is common in networking scripts. Awk is perfect for this because it's built into every Unix system and processes structured text efficiently.

Error Handling and Debugging

Production scripts need robust error handling. Don't assume commands will succeed.

#!/bin/bash

set -euo pipefail

ping_host() {
  local host="$1"
  if ! ping -c 1 -W 2 "$host" &> /dev/null; then
    echo "ERROR: $host is unreachable" >&2
    return 1
  fi
  echo "SUCCESS: $host is reachable"
}

# Call function and check exit code
if ping_host "8.8.8.8"; then
  echo "Proceeding with operations..."
else
  echo "Aborting: network unreachable" >&2
  exit 1
fi

set -e exits on any command failure. set -u errors on undefined variables. set -o pipefail catches failures in pipelines. Functions return exit codes (0 for success, non-zero for failure). Always check exit codes before proceeding—this prevents cascading failures.

Scheduling Scripts with Cron

Most networking tasks run repeatedly. Cron executes scripts on a schedule.

0 */6 * * * /usr/local/bin/host_monitor.sh

This runs the host_monitor.sh script every 6 hours. Edit your crontab with crontab -e. The format is: minute (0-59), hour (0-23), day (1-31), month (1-12), weekday (0-6, where 0=Sunday).

For critical monitoring, use */5 * * * * to run every 5 minutes. Log output to track results: 0 */6 * * * /usr/local/bin/host_monitor.sh >> /var/log/monitor.log 2>&1. This appends both stdout and stderr to the log file.

Best Practices for Production Scripts

Before deploying a script to production, follow these guidelines:

  • Use absolute paths: Write /usr/bin/curl instead of curl because cron jobs have limited PATH variables.
  • Add detailed comments: Future you will forget what the script does. Document the purpose, inputs, and outputs.
  • Validate inputs: Check that files exist and variables aren't empty before using them.
  • Log everything: Include timestamps and operation status. Logs are invaluable for troubleshooting failures.
  • Test thoroughly: Run the script on a test server before running it on production systems.
  • Handle cleanup: Remove temporary files and close connections properly.
