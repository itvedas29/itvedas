How to Monitor Linux Server Performance: Tools and Commands

Linux server performance monitoring requires understanding key metrics—CPU utilization, memory usage, disk I/O, and network throughput—and knowing which tools to use. The most effective administrators combine built-in commands like top, vmstat, and iostat with persistent monitoring solutions. This guide walks you through essential tools and real commands you'll use in production environments.

Why Linux Performance Monitoring Matters

Your database server is slow. Users complain. You need answers—fast. Without proper monitoring, you're flying blind. Performance issues stem from resource bottlenecks: a maxed-out CPU, memory swapping, slow disk I/O, or network saturation. Identifying which resource is the culprit requires systematic monitoring. Proactive monitoring also prevents incidents before they impact production.

For database administrators specifically, monitoring isn't optional—it's critical. A database experiencing high I/O wait can cripple your entire application stack. Memory pressure causes buffer pool eviction. CPU contention delays query execution. The right monitoring tools give you visibility into these problems in real-time.

Essential Monitoring Commands You Should Know

The top Command

top is your starting point. It's interactive, real-time, and available on every Linux system. Running top displays processes sorted by CPU usage, memory consumption, and more.

top

The output shows system uptime, load average, total memory, and a list of running processes. Press Shift+M to sort by memory usage instead of CPU. Press q to quit. For non-interactive output, use top -b -n 1 to get a single snapshot.

Key metrics to watch in top:

  • %CPU: CPU time consumed by each process
  • %MEM: Memory usage as percentage of total RAM
  • Load average: Number of processes waiting for CPU time (three numbers represent 1, 5, 15 minute averages)
  • VIRT/RES/SHR: Virtual, resident, and shared memory

The vmstat Command

vmstat reports virtual memory statistics. It's excellent for understanding memory pressure and I/O wait patterns over time.

vmstat 5

This command updates every 5 seconds. The first line shows averages since boot; subsequent lines show real-time data. Column breakdowns:

  • r: Processes waiting for CPU time
  • b: Processes in uninterruptible sleep (blocked on I/O)
  • swpd: Virtual memory used (kilobytes)
  • free: Free memory
  • wa: Percentage of CPU time spent waiting for I/O

High wa values indicate disk I/O bottlenecks. If swpd grows while free shrinks, you're experiencing memory pressure.

The iostat Command

For disk performance, iostat is indispensable. It shows per-disk and partition statistics including I/O operations, throughput, and wait times.

iostat -x 1

The -x flag enables extended statistics. The second argument (1) sets the interval in seconds. Key columns:

  • r/s, w/s: Read and write operations per second
  • rMB/s, wMB/s: Read and write throughput in megabytes
  • await: Average time for I/O requests (milliseconds)
  • %util: Percentage of time the disk is busy

High await values suggest disk latency issues. %util above 80% indicates the disk is heavily utilized and might be a bottleneck.

The sar Command

sar (System Activity Reporter) collects and reports historical performance data. Unlike top or vmstat, sar maintains a running log.

sar -u 1 5

This command shows CPU utilization for 5 intervals of 1 second each. Other useful options:

  • sar -r — Memory and swap usage
  • sar -b — I/O and transfer rate statistics
  • sar -n DEV — Network device statistics
  • sar -f /var/log/sa/sa01 — View historical data from specific date

The sar daemon runs in the background collecting data every 10 minutes by default. This makes it ideal for trend analysis and identifying when problems occurred.

Advanced Monitoring Tools for Production

Prometheus and Grafana Stack

For persistent, long-term monitoring, you'll want Prometheus collecting metrics and Grafana visualizing them. Prometheus scrapes metrics from exporters like node_exporter, which instruments system metrics. Grafana creates dashboards showing historical trends, spikes, and anomalies.

Installation involves deploying Prometheus to collect metrics, configuring node_exporter on monitored servers, and connecting Grafana for visualization. This requires infrastructure investment but pays dividends in production environments handling critical workloads.

Netdata for Real-Time Monitoring

netdata is a lightweight, real-time monitoring agent that requires zero configuration. It collects thousands of metrics automatically and provides an interactive web dashboard.

curl https://get.netdata.cloud/kickstart.sh | sh

Once installed, access the dashboard at http://your-server:19999. It monitors CPU, memory, disk, network, processes, and more. For database servers, Netdata can integrate with MySQL, PostgreSQL, and other databases to monitor query performance and connection pools.

Monitoring Database-Specific Metrics

Database Connection Pools

Monitor active connections and connection pool status. For MySQL, query the PROCESSLIST:

SHOW PROCESSLIST;
SHOW STATUS WHERE variable_name IN ('Threads_connected', 'Threads_cached', 'Threads_created');

For PostgreSQL, check active connections:

SELECT datname, count(*) FROM pg_stat_activity GROUP BY datname;

Slow Query Logs

Enable MySQL slow query logging to identify problematic queries:

SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 2;

Monitor the slow query log using mysqldumpslow to summarize patterns and identify offending queries for optimization.

Memory Buffers and Cache

For database servers, memory efficiency is paramount. Check the operating system's page cache and buffer pool:

free -h

This shows memory breakdown including buffers and cache. Database buffer pools are part of the resident memory (RES in top). Monitor whether your database's configured buffer pool is being fully utilized or if memory is being wasted on unnecessary caches.

Creating Custom Monitoring Scripts

You can automate monitoring with shell scripts that collect critical metrics and log them for analysis. Here's a simple example that logs CPU and memory metrics:

#!/bin/bash
while true; do
  echo "$(date '+%Y-%m-%d %H:%M:%S') - $(top -bn1 | grep 'Cpu(s)' | awk '{print $2}' | cut -d'%' -f1) CPU - $(free -h | grep Mem | awk '{print $3}') Memory used" >> /var/log/perf-monitor.log
  sleep 60
done

Save this as a systemd service or cron job. Over time, you'll build a dataset showing trends and patterns, helping you forecast capacity needs and identify recurring bottlenecks.

Best Practices for Linux Server Monitoring

  • Monitor baseline metrics: Know what "normal" looks like on your hardware. Establish baselines for CPU, memory, disk I/O, and network to recognize anomalies quickly.
  • Set up alerting: Don't just monitor—alert. Use tools like Prometheus alertmanager or custom scripts to notify you when metrics exceed thresholds.
  • Correlate metrics: High CPU + high I/O wait might indicate slow queries. High memory + high swap usage indicates memory exhaustion. Look for patterns, not single metrics.
  • Collect historical data: Commands like top show snapshots. Use persistent tools like sar, Prometheus, or Netdata to maintain historical records for trend analysis.
  • Focus on database metrics: System metrics are important, but database-specific metrics (query execution time, lock contention, cache hit ratios) often reveal root causes faster.
  • Test before production: Monitoring tools consume resources. Test their impact in staging environments before deploying to production.

Troubleshooting Common Performance Issues

High CPU Usage

Use top to identify which process consumes CPU. For database servers, check slow query logs and consider query optimization. Use perf for detailed CPU profiling if needed.

Memory Exhaustion

Run free -h and top sorted by memory. If swpd grows in vmstat, processes are swapping to disk—a critical performance killer. Reduce memory-consuming processes or add RAM.

Disk I/O Bottlenecks

iostat -x reveals disk saturation. High await values indicate slow drives or excessive I/O requests. For databases, optimize queries to reduce I/O, consider SSD upgrades, or implement read replicas to distribute load.

Network Saturation

Use iftop or nethogs to monitor network usage by connection or process. For database replication lag due to network issues, monitor sar -n DEV for packet loss or errors.

Frequently Asked Questions

What's the difference between top and vmstat?

top is interactive and process-focused, showing which applications consume resources. vmstat is system-focused and non-interactive, showing overall memory pressure, I/O wait, and context switches
